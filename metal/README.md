# metal (Terraform + Ansible port)

Terraform provisions Proxmox VMs and renders an Ansible inventory. Ansible
installs k3s and Cilium inside the guests. Same split pattern the
upstream `metal/` layer uses (Ansible only), except the "bare-metal boot"
step becomes "Terraform creates VMs on Proxmox".

## Layer mapping

| Upstream (Ansible) | This port |
| --- | --- |
| `boot.yml` — PXE + Wake-on-LAN | `terraform/` — `bpg/proxmox` clone of a Fedora cloud-init template |
| `cluster.yml` role `prerequisites` | `ansible/roles/pre_install` |
| `cluster.yml` role `k3s` | `ansible/roles/{k3s_server,k3s_agent}` |
| `cluster.yml` role `cilium` | `ansible/roles/post_install` |
| `cluster.yml` role `automatic_upgrade` | Not ported — cluster-side upgrades via `kured` + `system-upgrade-controller` in `system/` |

## Layout

```
tmp/metal/
├── Makefile                # all: terraform_apply install_k3s
├── terraform/
│   ├── versions.tf
│   ├── variables.tf
│   ├── vms.tf              # Proxmox VMs (was tmp/metal/vms.tf)
│   ├── ansible.tf          # renders inventory + generates k3s token
│   ├── inventory.tftpl     # ansible inventory template
│   ├── outputs.tf
│   └── terraform.tfvars.example
└── ansible/
    ├── ansible.cfg
    ├── playbook.yaml       # pre_install → k3s_server → k3s_agent → post_install
    ├── group_vars/all.yaml # k3s + cilium versions
    └── roles/
        ├── pre_install/    # sysctls, swap, packages
        ├── k3s_server/     # k3s config + install
        ├── k3s_agent/      # k3s agent, join via VIP
        └── post_install/   # Cilium helm + CRs + fetch kubeconfig
```

## Prerequisites

- **Proxmox VE** reachable from your workstation, API token with
  `PVEVMAdmin` + `PVEDatastoreUser` on the target node (or root for a homelab).
- **A cloud-init template** already on the Proxmox node (e.g. VMID 1000
  `fedora-cloud-init`). Terraform clones it; it does not build one for you.
  Set `template_vm_id` in `terraform.tfvars` to that VMID.
- **SSH keypair** at `~/.ssh/id_ed25519` (override with `ssh_private_key_path`).
  Terraform reads the `.pub` and Proxmox's cloud-init drive injects it as the
  target user's only authorized key on every clone; Ansible uses the private
  half to reach the guests.
- **Ansible ≥ 2.15** with `kubernetes.core` collection and the
  `kubernetes` + `PyYAML` Python packages on the control node:
  ```sh
  ansible-galaxy collection install kubernetes.core
  pip install kubernetes PyYAML
  ```

## Usage

```sh
cp terraform/terraform.tfvars.example terraform/terraform.tfvars
$EDITOR terraform/terraform.tfvars
make            # terraform apply → ansible-playbook
```

`terraform_apply` boots the VMs and writes `ansible/inventory.ini`.
`install_k3s` runs the playbook, which finishes by dropping the kubeconfig at
`ansible/kubeconfig`.

## Kubeconfig location

The parent Makefile (`homelab/Makefile`) exports
`KUBECONFIG = $(shell pwd)/metal/kubeconfig.yaml`. When this port replaces the
real `metal/` directory, symlink or copy `ansible/kubeconfig` to
`metal/kubeconfig.yaml` — or update the parent Makefile at the same time.

## What's intentionally different from upstream

- **No PXE / WoL.** Proxmox clones VMs from a cloud-init template you built
  once by hand; provisioning is `terraform apply`.
- **Template built out-of-band.** Terraform does not download a cloud image
  or render cloud-init snippets — it only clones `template_vm_id` and hands
  Proxmox the per-VM hostname, IP, and SSH key via the built-in Cloud-Init
  drive (`initialization.user_account` / `ip_config`). Rebuild the template
  when you want a newer base image.
- **Cluster token is generated by Terraform** (`random_password.k3s_token`)
  rather than by the first Ansible run. Treat `terraform.tfstate` as a
  secret; encrypted remote backend recommended.
- **Automatic OS upgrades** are cluster-side (`kured` + upgrade controller
  in `system/`) rather than node-side `dnf-automatic`.
